# 论文知识引擎故障与修改方案 Q&A

> 适用项目：paper-knowledge-engine
> 当前方向：FSD 论文知识库（fsd）
> 维护日期：2026-09-07
> 当前目标：L2 级、可追溯的普通 Wiki；暂不调用 LLM。

本文记录项目建设过程中反复出现的问题、根因、已经实施的修改、恢复方法，以及尚未完成的架构补强。遇到新问题时，先按本文判断阶段，再决定是恢复 run、单独发布 Evidence，还是修改代码。

## 0. 先看结论

主线流程是：

    OpenCLI / arXiv 检索
      → 规则筛选与选篇冻结
      → 下载 PDF
      → 本地 MinerU 解析
      → Archive 校验归档
      → Evidence 发布到 Obsidian

当前系统的几个边界：

- FSD 是 paper 类型方向库，不默认选择；启动后必须选择方向，或显式传入 --library fsd。
- 当前 FSD 有 8 个检索方向，每个方向查询 submitted 和 updated 两种日期模式，共 16 个检索分片。
- current 任务的日期起点来自 config/fsd/library.yaml 的 start_date，当前是 2026-01-01。
- MinerU 使用本机安装、模型和 GPU；任务级 API 绑定本机回环地址，不是远程 API。
- Archive 是机器可验证的事实包；Evidence 是 Obsidian 阅读层；两者都保留所需的 PDF 和资源副本。
- MinerU Markdown、分页文本、来源 PDF 和资源会保留；目前不生成 LLM 摘要、标签或推理结论。
- L3 人工知识层尚未自动化。人工笔记应放在托管 Evidence 目录之外。

## 1. 当前目录和一篇论文的路径

### Q1：代码、状态、PDF、Obsidian 分别保存在哪里？

A：活动路径如下，不能再使用旧的 fsd-code2doc 根：

| 内容 | 当前路径 |
| --- | --- |
| 项目代码 | D:/agent-data/backend/projects/paper-knowledge-engine |
| FSD 数据库、Archive、run、操作记录 | D:/agent-data/data/paper-libraries/fsd |
| FSD 原始 PDF | D:/paper/paper-knowledge-engine/fsd |
| FSD Obsidian Vault | D:/obsidian/data/paper-knowledge-engine/fsd |
| FSD 备份根 | D:/agent-data/backups/paper-libraries/fsd |

引擎的共用根配置在 config/machine.local.yaml：

    roots:
      data_libraries_root: D:/agent-data/data/paper-libraries
      backup_libraries_root: D:/agent-data/backups/paper-libraries
      pdf_libraries_root: D:/paper/paper-knowledge-engine
      vaults_root: D:/obsidian/data/paper-knowledge-engine

### Q2：具体到一篇论文，完整路径是什么？

A：假设论文为 2609.00001v1，标题为 Example Paper，主分类为 AI-FSD：

    原始 PDF：
    D:/paper/paper-knowledge-engine/fsd/01-AI-FSD-Specification/2609.00001v1_Example-Paper.pdf

    Archive：
    D:/agent-data/data/paper-libraries/fsd/archive/2609.00001-v1/
    ├── source.pdf
    ├── document.md
    ├── pages.json
    ├── content-list.json
    ├── source.json
    ├── manifest.json
    └── assets/

    Obsidian：
    D:/obsidian/data/paper-knowledge-engine/fsd/Evidence/papers/2609.00001-v1/
    ├── paper.md
    ├── pages.md
    ├── source.pdf
    └── assets/

Archive 已取消旧的 papers 包装层，因此 Archive 直接使用 <baseId>-v<version>。Obsidian 的 Evidence v3 契约仍保留 Evidence/papers/，这是两个层次不同的目录，不能混用。

### Q3：为什么原始 PDF、Archive 和 Obsidian 都有 PDF？

A：三份 PDF 用途不同：

1. D:/paper/... 是下载原件，便于长期保存和人工打开。
2. data/.../archive/.../source.pdf 是经过哈希和 manifest 绑定的不可变事实副本，用于校验、重建和发布。
3. obsidian/.../Evidence/.../source.pdf 是 Obsidian 阅读副本，和发布的 paper.md、pages.md、assets/ 放在一起。

不能为了节省空间直接删除 Archive 或 Evidence 内的副本。需要清理时，只能按 cleanup/reconcile 计划处理临时 work/，不能把 PDF 原件、Archive 或托管 Evidence 当作缓存。

## 2. CLI、方向库和配置

### Q4：为什么去掉 PowerShell 菜单外壳？

A：菜单入口已经统一为 Bun 自身：

    cd D:/agent-data/backend/projects/paper-knowledge-engine
    bun src/cli.ts

PowerShell 脚本仍可作为 MinerU/process supervisor 等运维工具保留，但不再作为论文任务菜单入口。菜单和命令路由位于：

- src/cli/menu.ts
- src/cli/routes.ts
- src/cli.ts

这样可以保证交互菜单、显式命令、测试调用使用同一套 Bun 逻辑。

### Q5：为什么现在不能默认进入 FSD？

A：引擎后续会同时支持多个方向库。默认 FSD 会让用户误把任务、数据库、PDF 或 Obsidian 内容写入错误方向。

启动菜单先选择方向：

    bun src/cli.ts

显式运行命令必须指定方向：

    bun src/cli.ts --library fsd run-task --mode current
    bun src/cli.ts --library fsd run-task --mode weekly
    bun src/cli.ts --library fsd evidence-publish --run-id RUN_ID

新增方向时，在 config/<libraryId>/ 中放入该方向所需配置，并由 library_id、路径派生和操作记录隔离状态。不能复制一套 FSD 代码来实现新方向。

### Q6：FSD 的检索种类到底是多少？

A：目前是 8 个检索方向，不是 12 个。

| 检索方向 | 重点 |
| --- | --- |
| AI-FSD | 功能规格、需求恢复 |
| LLM-Wiki | 代码仓库文档、Wiki |
| AI-TDD | 测试生成、修复 |
| AI-DDD | 领域模型、业务规则 |
| AI-Program-Analysis-AST | 程序分析、AST |
| Code-Translation | 代码翻译、迁移 |
| Verification | 语义等价、行为保持 |
| Evaluation | 评测、基准 |

每个方向各有 submitted 和 updated 两种日期模式，因此任务计划是 8 × 2 = 16 个分片。

config/fsd/categories.yaml 的 12 个条目是 PDF 分类目录映射，不是 12 个独立的 arXiv 检索任务。没有独立检索任务的分类只能作为归类结果，不能据此判断发现阶段应有 12 个请求。

### Q7：为什么曾经出现 2026-09-01 → 2026-09-04，而不是配置日期？

A：这是日期窗口来源混用造成的错误。current 任务的权威起点必须是：

    config/fsd/library.yaml
    start_date: 2026-01-01

修正后的规则：

- current：start_date 到当前时间。
- weekly：根据成功水位和 overlap_hours 计算增量窗口。
- --from、--to：只有显式传入时才覆盖默认窗口。
- 成功水位不能缩短 current 的配置起点。

因此正常执行：

    bun src/cli.ts --library fsd run-task --mode current

应显示 2026-01-01 → 当前日期，而不是以数据库最近一次启动时间作为 current 起点。

### Q8：engine.yaml、paper-policy.yaml、categories.yaml 各自负责什么？

A：当前配置已经按共用引擎、机器和方向拆开：

| 文件 | 作用 |
| --- | --- |
| config/engine.yaml | 共用 arXiv、MinerU、运行时和 Evidence 参数 |
| config/machine.local.yaml | 本机路径、代理、MinerU 安装、模型和 GPU |
| config/fsd/library.yaml | FSD 身份、日期、任务上限、配额和周调度 |
| config/fsd/query-matrix.yaml | FSD 检索方向、查询、分类和日期模式 |
| config/fsd/paper-policy.yaml | 纳入、排除、优先级和硬过滤 |
| config/fsd/categories.yaml | PDF 分类目录映射 |

旧的单体配置不是活动配置来源。未知字段和未知方向库会被严格拒绝，避免配置悄悄失效。

## 3. MinerU 解析问题

### Q9：MinerU 已经本地部署，为什么日志里还出现 API？

A：日志中的 API 是本机任务级 API，不是临时远程服务，也不代表 MinerU 没有本地部署。

当前过程是：

1. CLI 读取本机 MinerU、模型、GPU 和运行参数。
2. 在 127.0.0.1:17860 启动本地 MinerU API。
3. 当前解析操作内的论文共享这个本地 API。
4. 操作成功、失败或中断后回收服务和安全记录。

相关配置位于 config/engine.yaml 的 mineru.api_host、api_port 和 api_startup_timeout_seconds。模型和权重仍来自 machine.local.yaml 指定的本地目录。

这里的任务级 API 是为了隔离任务、复用模型进程和统一清理；它不是一个系统常驻服务。若要改成常驻 MinerU 服务，必须另行设计健康检查、版本锁、并发隔离、崩溃恢复和跨任务租约，不能只把端口固定就视为稳定服务。

### Q10：MinerU 的 Batch Ratio 是什么？

A：pipeline_batch_ratio 是 Pipeline 内部推理批量的兼容参数，通过 MinerU 的虚拟显存设置影响单次 GPU 推理批量。

当前配置：

    pipeline_batch_ratio: 1
    max_concurrency: 1
    processing_window_size: 1

三者含义不同：

- pipeline_batch_ratio：单次 Pipeline 推理批量倾向。
- max_concurrency：API 请求并发数。
- processing_window_size：一次处理的页窗口大小。

VLM 的 vlm_batch_size 只在 VLM 模式下生效。日志自动选择 Batch Ratio: 4 时，表示 MinerU 根据显存估算出的内部批量，不等价于同时解析 4 篇论文，也不等价于把任务并发改成 4。

### Q11：process_error、Layout Predict 0% 是什么问题？

A：这类错误表示 MinerU 子进程或本地 API 在具体解析阶段失败，常见位置是模型初始化后进入 Layout 推理。它不是 arXiv 检索错误，也不是 Evidence 发布错误。

排查顺序：

1. 查看失败论文的解析记录和 MinerU 原始 stderr。
2. 检查本机 GPU、CUDA DLL、模型目录和 MinerU 版本/commit。
3. 确认任务级 API 能启动并通过健康检查。
4. 单独使用 parse-local --base-id BASE_ID --reparse 重试失败论文。
5. 确认没有残留 operations/locks/processes/ 安全记录。

相关实现：

- src/mineru/mineru-api-session.ts
- src/mineru/mineru-local-jobs.ts
- src/mineru/mineru-local-result.ts
- src/runtime/process.ts

不要因为一篇论文失败就删除整个 run、数据库或所有 Archive。任务会保留固定选篇和检查点，恢复时优先复用已下载内容。

### Q12：为什么会出现 invalid_artifact？

A：invalid_artifact 是归档内容不满足安全或引用契约，不是一个单独的网络错误。已经遇到过以下具体类型：

| 报错 | 根因 |
| --- | --- |
| HTML img element must have a parseable src or srcset attribute | MinerU 输出了无法解析的 HTML 图片引用 |
| unsafe Archive path | 资源路径可能越界、包含不安全片段或不符合归档路径规则 |
| Markdown image reference has no destination | Markdown 图片语法缺少目标路径 |
| ENOENT ... Archive.Archive | 解析结果目录和归档读取契约不一致，目标 Archive 不存在 |
| ENOENT .../auto/LOC（或 ORG、PRODUCT、TYPE） | MinerU 的代码示例使用 `[实体](实体类型)` 标注，旧引用扫描器把实体类型误判为本地资源路径 |
| ENOENT .../auto/refs/x.md | MinerU 保留了正文中的概念性仓库链接 `[X](refs/x.md)`，旧引用扫描器把占位路径误判为本地资源 |
| Markdown image reference has no destination：外部 URL 以 `...` 截断 | MinerU 截断了表格中的外部图片 Markdown，缺少右括号；该图片不是本地 Archive 资源 |
| ENOENT .../auto/url | MinerU 在提示词示例中保留了 `Images need to be rendered as ![](url)`；`url` 是空 alt 图片的通用占位符，不是输出目录中的本地资源 |
| archive manifest path must be a safe relative POSIX path | MinerU 把 Python 代码中的 `[self.\_message\_criteria[self.\_current\_msg]](self.\_state)` 保留成了 Markdown 链接形状；反斜杠转义下划线不是资源路径，旧扫描器把它交给 Archive 路径校验而失败 |
| archive manifest path must be a safe relative POSIX path：`\\*\\*tc.args` | MinerU 把 Python 关键字参数展开 `registry[tc.name](\\*\\*tc.args)` 保留成了 Markdown 链接形状；旧扫描器只识别属性下标形式，未识别参数展开语法 |
| ENOENT .../auto/required/optional | 工具参数说明使用 `[{type}](required/optional)` 表示参数状态，旧引用扫描器把说明文本误判为本地资源目录 |
| unsafe Archive path：`{{layer:...}}` | MinerU 保留了模板化 HTML 示例，`<img src="{{layer:...}}">` 是渲染占位符，不是本地文件；旧扫描器把占位符交给 Archive 文件名校验 |
| ENOENT .../auto/=0 | 化学 SMILES 中的氧原子 `O` 被 MinerU/OCR 识别成数字 `0`，`[N+:17](=0)` 被链接扫描器误判为资源路径 |
| ENOENT .../auto/=O（以及 `=[OX1]`、`[`） | MinerU 的代码示例使用 SMARTS 化学模式（如 `[CX3](=O)`、`[CX3](=[OX1])`、`[OD2]([#6])`）；旧扫描器只识别普通 SMILES，误把化学键/原子谓词当作 Archive 路径 |
| ENOENT .../auto/OC | MinerU 的分子式示例把多原子 SMILES `[C@H](OC)` 保留成了 Markdown 链接形状；旧扫描器只识别单个原子，误把 `OC` 原子序列当作 Archive 路径 |

修正方向：

- 在 Archive v2 写入前规范化 Markdown、HTML 图片引用和资源路径。
- 对所有资源引用做路径边界检查，禁止 ..、绝对路径和未绑定资源。
- manifest 必须列出实际存在的资源，引用不能指向 manifest 外的文件。
- Archive reader 和 Evidence publisher 只接受验证后的 Archive。
- 失败时保留原始解析记录，禁止忽略错误后发布半成品。

主要代码位置：

- src/shared/archive-v2.ts
- src/shared/archive-references.ts
- src/evidence/archive-reader.ts
- src/evidence/publisher.ts

这类错误的防重复策略不是简单重试同一份脏结果，而是先修正归一化和校验边界，再只重新解析失败论文。

## 4. arXiv、OpenCLI 和下载问题

### Q13：浏览器可以访问 arXiv，为什么 OpenCLI 仍然失败？

A：浏览器访问首页和 Bun/OpenCLI 访问 API 不是同一条网络路径。浏览器可能使用系统代理、PAC、浏览器 DNS 或独立网络栈；OpenCLI 子进程使用的是 Bun 继承的环境、配置代理和 API 主机。

先使用相同 Bun 运行时执行探针：

    bun src/cli.ts --library fsd arxiv-check --format json

探针只发一条小请求，不创建 run、PDF、Archive 或 Evidence。

配置含义：

- network.http_proxy：PDF 下载和默认网络代理。
- network.opencli_proxy_mode：OpenCLI 的 configured、direct 或 inherit 路由。
- network.arxiv_api_base：允许的 arXiv API 地址。

OpenCLI 的代理环境在子进程边界构造，不会修改父 PowerShell 环境；MinerU 本地 API 仍直连回环地址。

### Q14：OpenCLI installation manifest missing or invalid 怎么处理？

A：这说明 OpenCLI 本地适配器没有准备好、版本/源哈希过期，或项目依赖与安装 manifest 不一致。它不是 arXiv HTTP 失败。

先执行：

    bun src/cli.ts --library fsd opencli-prepare

然后再运行：

    bun src/cli.ts --library fsd arxiv-check --format json
    bun src/cli.ts --library fsd run-task --mode current

OpenCLI 的安装和运行时由 src/runtime/opencli.ts、src/discovery/opencli-install.ts 和 src/discovery/opencli-runner.ts 管理。不要直接调用全局 opencli，也不要手动复制 manifest。

### Q15：arXiv 的 429、503、ECONNRESET 分别是什么？

A：三类错误必须区分：

| 错误 | 含义 | 处理 |
| --- | --- | --- |
| HTTP 429 | 上游请求限流或容量不足 | 保存分片检查点，按冷却时间恢复 |
| HTTP 503 | API 暂时不可用 | OpenCLI 重试；耗尽后任务失败并可恢复 |
| ECONNRESET 等 transport error | 尚未收到可靠 HTTP 响应，连接被重置/中断 | 按瞬态错误退避重试，耗尽后从检查点恢复 |

当前 arXiv 发现默认请求间隔为 6 秒，最多 6 次尝试，容量冷却默认 900 秒。看到 ARXIV_CAPACITY_LIMITED 时不要连续点击重试，也不要删除数据库或 checkpoint。

任务级路由和重试实现位于：

- src/discovery/arxiv-transport.ts
- src/discovery/opencli-runner.ts
- src/discovery/checkpoint.ts
- opencli/arxiv/retry.ts

### Q16：下载遇到 404、arXiv file unavailable 或 socket connection closed 会不会把整批都弄坏？

A：404/410 和连接中断的处理不同：

- 404/410 被视为该版本 PDF 永久不可用，当前实现会标记该论文并尝试使用同方向 fallback 候选，不应因为一篇论文直接结束整个下载阶段。
- HTTP 5xx 且响应正文明确包含 `file unavailable` 表示 arXiv 已有论文元数据，但该版本 PDF 资产暂未可用；当前实现延期该论文、不做永久排除，优先用同方向 fallback 补位并继续任务，后续任务可再次尝试。
- arXiv 论文 PDF 不受 `mineru.local_import.max_pdf_pages` 的本地导入页数上限约束；下载仍保留 200 MB 文件大小保护，页数由后续 MinerU 任务超时和资源策略约束。
- ECONNRESET、ECONNREFUSED、ETIMEDOUT 等瞬态错误会做指数退避重试。
- 普通 HTTP 5xx、429 或瞬态错误在所有尝试中都失败，当前任务仍会失败，但已下载论文和选篇 checkpoint 会保留；下一次执行会复用已完成内容。
- PDF 先写入 .part 临时文件，校验为 PDF 且解析页数通过后才原子移动到目标目录。

实现位置为 src/library/sources/pdf-store.ts。不要手动把失败的 HTML 响应改名为 PDF，也不要删除 .part 以外的已验证文件。

## 5. Archive、Evidence 和 Obsidian 发布问题

### Q17：为什么解析成功，Evidence 发布还会失败？

A：解析成功只代表单篇 MinerU 结果已经生成；Evidence 发布还要验证整个 run 的 Archive manifest、资源引用、哈希和发布事务。

曾经出现过：

- lstat ... extracted/<baseId>：发布器找不到应归档的解析目录。
- referenced asset is absent from Archive manifest：Markdown 引用了 manifest 未登记的资源。
- EVIDENCE_CONFLICT: unknown manual file ...：Vault 中存在不属于当前托管清单的旧手工文件或旧布局文件。

修改方案：

- 先把 MinerU 输出整理为 Archive v2，再发布 Evidence v3。
- Archive manifest 是资源和哈希的唯一边界。
- 发布前验证 PDF、Markdown、页文本、content-list 和 assets。
- Evidence 发布使用 publication journal、receipt 和独立 publication lock。
- 失败恢复只重放完整 Archive，不重新下载和重新解析。

### Q18：Evidence 发布失败后应该怎么做？

A：只使用原 run ID 恢复，不要创建新的手工目录，也不要直接复制文件：

    bun src/cli.ts --library fsd evidence-publish --run-id RUN_ID
    bun src/cli.ts --library fsd reconcile

如果是普通解析失败，应重新执行 current/weekly 任务，让任务恢复固定选篇和解析。菜单 6 只适用于已经有可验证 Archive、但 Evidence 发布阶段失败的 run，不用于恢复 discovery 或 download。

### Q19：Obsidian 中人工文件和托管文件如何区分？

A：

- Evidence/papers/ 和 Evidence/indexes/ 是自动托管区域，不能手动改名、移动或添加未知文件。
- 人工笔记、阅读批注和后续 L3 内容放在 Evidence 之外。
- .obsidian/ 是 Vault 设置，不属于论文发布内容。
- 发布器不会创建或覆盖人工知识层。

如果旧 Vault 混有多个历史布局，先运行 reconcile 或经过审查的 vault rebuild，不要直接全盘删除。

## 6. run、job、恢复和“直接结束”

### Q20：为什么日志里会出现“恢复 run xxx”？

A：runId 和 jobId 不是一回事：

- runId：一次 current/weekly 论文批次的持久身份，包含窗口、选篇、分片 checkpoint、解析清单和发布状态。
- jobId：一次 CLI 操作请求的身份，负责操作状态、owner、stage、锁和恢复入口。

失败后再次执行时，可以新建一个 job，但复用同一个未完成 run。这样已经完成的 discovery 分片、下载 PDF 和固定选篇不会丢失。

### Q21：为什么最近会在 12/16 后直接回到 PowerShell？

A：最近一次记录显示这不是正常完成，而是运行 Bun 的主进程在第 12 个发现分片完成后被外部终止：

- 操作记录 3187fcb8-4301-4196-a6db-18ad7a78a734 停留在 running、acquire、12/16。
- 事件日志最后一条是 discovery-shard-complete，没有 task-complete、task-failed 或 interrupted。
- owner PID 38928 已不存在，但 workflow lock 仍残留。

这类记录通常来自 Ctrl+C、终端关闭、外部进程终止或 Bun/Windows 进程崩溃；从现有项目日志只能确定是主进程非正常消失，不能单凭记录区分具体触发者。它不是 arXiv 返回空结果，也不是任务成功。

恢复方法：

    bun src/cli.ts
    选择 FSD
    选择 2. 运行当前任务

操作存储会识别死亡 owner，把遗留操作标记为 interrupted，任务状态会复用 run 的 discovery checkpoint，跳过已经完成的分片。不要手动删除 workflow.lock、数据库或 runs。

### Q22：这个“直接结束”问题是否已经完全修复？

A：当前已经具备死 owner 检测、操作恢复和 checkpoint 复用，但“前台交互式 Bun 主进程被杀时仍能保证后台任务继续运行”尚未彻底完成。

现状：

- 正常异常会被 workflow 捕获并写入 failed 状态。
- 可恢复的外部中断会在下一次读取/提交操作时被标记为 interrupted。
- 已完成的发现分片会持久化，不会因为前台进程消失而丢失。
- 但是长任务仍直接运行在交互式 CLI 进程中；如果该进程被强制终止，当前任务不会即时写入终态。

推荐的后续方案：

1. 由 Bun CLI 只负责 admission 和展示。
2. 通过固定的 worker 子进程执行长任务。
3. CLI 退出不终止 worker；worker 独立写 job/event/run 状态。
4. 菜单重新进入时读取事件并显示任务状态。
5. 只有 worker 自己确认取消或失败时才写入终态。

这属于运行架构升级，不应通过简单删除锁或捕获一个异常来伪装成已解决。

## 7. 输出、日志和调试信息

### Q23：为什么成功后曾经打印巨大 JSON？

A：旧的 routeCommand 在任务结束时直接把 business result 或 JobView 全量打印，包含 selected、window、requestId、路径和内部结构，导致成功后的终端难以阅读。

当前修改：

- 运行中的进度日志仍保留，避免长任务看起来像卡死。
- 任务结束只打印简短摘要：

    [任务] 成功：已处理 79 篇论文

- 失败只打印阶段、runId 和简短原因：

    [任务] 失败：parse；runId=RUN_ID；原因：OPERATION_FAILED

- 传入 context.output 的测试和程序调用仍能拿到完整结构化结果。
- 配置查看、任务预览等本来就需要展示结构化数据的命令仍保留 JSON。

实现和测试位于：

- src/cli/routes.ts
- tests/cli-menu.test.ts

## 8. 日常恢复流程

### Q24：发现阶段失败怎么办？

1. 先看错误是 ARXIV_CAPACITY_LIMITED、transport error、OpenCLI manifest，还是其他异常。
2. OpenCLI manifest 问题先执行：

       bun src/cli.ts --library fsd opencli-prepare

3. 网络问题先执行：

       bun src/cli.ts --library fsd arxiv-check --format json

4. 限流冷却结束后重新执行同一方向、同一模式：

       bun src/cli.ts --library fsd run-task --mode current

5. 不要更改日期、不删除数据库、不删除 checkpoint。

### Q25：下载阶段失败怎么办？

1. 重新执行同一 current/weekly 命令。
2. 已下载且通过哈希验证的 PDF 会复用。
3. 404/410 会被标记为不可用并尝试 fallback。
4. 连接错误会按配置重试；如果仍失败，保留 run 后稍后恢复。
5. 不要把失败的 HTML 响应当作 PDF 保存。

### Q26：解析阶段失败怎么办？

1. 保留原 run 和解析记录。
2. 如果错误是 `unparseable HTML attribute value`，先检查失败产物中的 Markdown 是否包含数学比较文本（例如 `<V`）；Archive v2 在尚未进入真实 `src/href/srcset` 资源属性时会保留这类伪标签，普通比较表达式不会再中断解析。
   如果错误是 `archive manifest path must be a safe relative POSIX path`，检查诊断目录中是否存在带 `\_` 的 Python 属性示例。当前归一化器只跳过同时具备转义下划线、点号和下标结构的代码记法；普通反斜杠、绝对路径、`..` 和未绑定资源仍会严格失败。
   如果错误值类似 `\\*\\*tc.args`，检查是否为 `registry[tc.name](\\*\\*tc.args)` 这类 Python 参数展开；归一化器只在两侧对象名一致的点号参数展开上下文中跳过，真实资源路径仍会校验。
   如果错误是 `ENOENT .../required/optional`，检查正文是否包含 `[{type}](required/optional)` 这类参数状态说明；归一化器只忽略带花括号类型标签的该固定记法，普通资源链接仍会校验。
   如果错误是 `unsafe Archive path` 且值类似 `{{layer:...}}`，检查是否为模板化 HTML 示例；归一化器只忽略带命名空间和冒号的双花括号占位符，真实 HTML 资源仍会校验。
   如果错误是 `ENOENT .../=0`，检查正文是否包含化学 SMILES 的 `[原子](=0)` 片段；该形式只在化学原子上下文中按 OCR 氧原子处理，普通 `=0` 资源链接仍会校验。
   如果错误是 `ENOENT .../=O`、`.../=[OX1]` 或 `.../[`，检查代码示例中是否出现 `[CX3](=O)`、`[CX3](=[OX1])`、`[OD2]([#6])` 等 SMARTS；归一化器只在有效化学原子/键上下文中跳过 SMARTS 谓词，普通 Markdown 资源链接仍会校验。
   如果错误是 `ENOENT .../OC`，检查是否为 `[C@H](OC)` 这类多原子 SMILES；归一化器只在化学原子标签后识别合法的多原子序列，普通 `OC` 资源链接仍会校验。
   如果错误是 `ENOENT .../url`，检查是否为 `Images need to be rendered as ![](url)` 这类提示词示例；归一化器只忽略带说明性上下文的空 alt `url` 占位符，带 alt 文本或 `assets/url` 的真实引用仍会校验。
3. 检查 MinerU 本地 API、GPU、模型目录和错误类型。
4. 先重试同一任务，让系统恢复固定选篇。
5. 必要时单独执行：

       bun src/cli.ts --library fsd parse-local --base-id BASE_ID --reparse

6. 只对失败论文重新解析，不清空整个 Archive。

### Q27：Evidence 发布阶段失败怎么办？

1. 确认 Archive 是否完整并存在 manifest。
2. 使用原 run ID：

       bun src/cli.ts --library fsd evidence-publish --run-id RUN_ID

3. 发布后执行：

       bun src/cli.ts --library fsd reconcile

4. 如果出现 journal 或 receipt 冲突，不要手工覆盖；保留两份文件，先分析冲突。

### Q28：为什么会出现 `completed publication Evidence manifest identity differs`？

A：这不是本次 PDF 下载、MinerU 解析或 Archive 损坏，而是“历史 Evidence receipt 不可变”与“当前确定性 renderer 输出”之间的身份冲突。典型情况是 renderer 修复了历史 Markdown 中的资源路径：Archive 的 `archiveManifestSha256` 没变，但当前从同一 Archive 重算的 `evidenceManifestSha256` 变了。旧 receipt 仍然正确，不能直接改写；如果放行也会失去历史可审计性。

本次 Agent Engineering run `24c4a15c-7208-4f35-9569-0dc7e360063f` 已完成 450 个 Archive 来源，最终在发布阶段发现历史 run `a2d88138-d720-4876-9b33-f1f9f015f2bc` 的一个来源 `2609.04749v1` 只有 `paper.md` 的链接从 `images/...` 变为 `assets/images/...`；Archive 身份未变。根因是当前 renderer 已修复旧链接，但历史发布没有经过 renderer-upgrade baseline 迁移。

恢复必须按以下顺序执行，并且只做一次：

1. 为现有 Vault 做可恢复备份，把旧 Vault 作为独立 `OLD_VAULT_ROOT` 保留；`OLD_VAULT_ROOT` 必须位于所有运行时根目录之外，尤其不能放在 `backupRoot`（例如 `D:\agent-data\backups\paper-libraries\agent-engineering`）里面，否则会被路径安全校验拒绝；不要删除 Vault、receipt、publication 或 SQLite。
2. 对当前完整 Archive 执行 `vault-rebuild --dry-run --format json`，审阅计划并保存 SHA-256；确认旧 Vault 和目标 Vault 是两个不重叠目录后再 `--apply`。
3. 执行 `evidence-renderer-baseline --dry-run --format json`，审阅输出后保存 baseline 文件及 SHA-256；再执行 `--apply`。该步骤只写 SQLite 的 singleton baseline，不改旧 receipt 或 publication 行。
4. 使用原 run ID 执行 `evidence-publish --run-id RUN_ID`，最后运行 `reconcile`。

现在普通 paper `run-task` 会在 discovery 前复用同一历史校验；后续若再发生 renderer 升级，任务会立即阻止并提示 `evidence-renderer-baseline`，不会先下载、解析大量论文再失败。未经过审阅的 baseline 不能通过 apply 的 Archive、Vault、receipt、历史顺序和内容哈希验证。

### Q29：什么时候可以清理？

A：只有以下内容可以按计划清理：

- 已确认无活动 owner 的临时 process safety record。
- 已完成任务产生的临时 work 文件。
- 经过 dry-run、哈希确认和 apply 的旧迁移 staging。

以下内容不能直接删除：

- library.sqlite
- runs/
- operations/
- archive/
- Obsidian 的托管 Evidence/
- 仍可能被恢复的 .part、publication journal 或 process record

清理命令必须先 dry-run，并保存计划和 SHA-256。不要使用全目录清空或手动删除锁来解决业务错误。
